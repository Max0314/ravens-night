# 鸦钟夜话开房、阵容与单人调试实施方案

基线为 `aa7438c`，已核对 Fribench ops 主线 `35c2a1dd55a9f2e93a0cd07c21ce77502e80990f`。本方案供下一步实施和验收，发布事实另记统一部署文档。

## 1. 产品边界与代码职责

| 模块 | 负责事项 |
| --- | --- |
| Web `App.tsx`、`Home.tsx`、`AccountPanel.tsx` | 开房前置授权、账号变化、个人栏口令查看与复制、标题三击、返回和历史层 |
| Web `Create.tsx`、`RoomPageShell`、新增滚轮与阵容编辑组件 | 保留原昵称头像，处理滚轮、构成校验、固定操作栏及提交草稿 |
| `@ravens/game-engine` 的 setup 与 setup-roles 模块 | 人数基础表、合法性、可抽候选组合、指定角色与实际发牌，输出纯函数结果 |
| Server `app.ts`、`RoomService`、`LiveRoomRuntime`、房间与创建回执 | 受信账号免码，游客授权和可复制凭据，单人房创建和隔离、持久化、幂等及恢复 |
| `Lobby`、`TestRolePicker`、`EffectsPreview` | 单人房的本人头像入口、角色选择、调试预览及返回大厅 |
| `GlobalAudioButton`、`AudioSettings` 和音频播放模块 | 统一音符面板、各通道的设置和播放，独立预览声音与试听清单 |

普通房沿用公开邀请码、二维码和受邀游客入座。手动人机补位仍属普通房功能。单人调试房只有房主和人机，自动补足已准备人机，房主可为自己选角色。动画与音频预览只在调试房大厅使用。订单、角色禁用、难度滑杆、日夜击杀与结算规则不在本批。

## 2. 登录免码与游客口令

### 2.1 状态及接口

保留现有 `ROOM_CREATE_PASSCODE` 配置、签名 `ravens_room_create_access` Cookie 与它的续存方式。没有口令配置的环境保持开放。授权优先级为已受信 Fribench 账号、开放配置、有效游客 Cookie、需要口令。浏览器本地账号信息仅用于展示，服务端沿现有 `accounts.get(request)` 身份结果作授权。

| 接口与输入 | 应答及持久化 |
| --- | --- |
| `GET /api/room-create-access` | 保留原 `status` 枚举。已登录返回 `{status:"GRANTED",via:"ACCOUNT"}`，开放配置返回 `{status:"OPEN",via:"OPEN"}`，持游客资格返回 `{status:"GRANTED",via:"PASSCODE"}` 并续存原 Cookie，其他返回 `{status:"PASSCODE_REQUIRED"}`。账号免码不会给浏览器发游客资格。 |
| `POST /api/room-create-access`，`{passcode:string}` | 只在游客且启用口令时验证。按现行对首尾空格的处理，比对当期配置，已经持有资格也必须真实比对。成功返回 `{status:"GRANTED",via:"PASSCODE",saved:true}` 并写资格及保存凭据。错码返回现有 `403 ROOM_CREATE_PASSCODE_INVALID`，保留此前有效授权与已存内容。账号已登录或口令功能关闭时用 GET 对应状态结束，`saved:false`。沿用现有验证限流，429 使用已有稍后重试口径，开房资格本身不限次数。 |
| `GET /api/room-create-access/saved` | 仅对有效资格游客提供 `{status:"MISSING"|"CURRENT"|"ROTATED"}`。无权限返回 403 和空的业务信息。 |
| `POST /api/room-create-access/saved`，`{intent:"REVEAL"}` | 再校验当前账号为游客、口令功能启用、资格 Cookie 和保存凭据有效。成功返回 `{status:"CURRENT"|"ROTATED",passcode:string}`，凭据缺失或失效返回 `404 SAVED_PASSCODE_UNAVAILABLE`。登录账号在此也拒绝读取。 |
| `POST /api/rooms` | 已提交的创建回执按原创建身份及指纹重放。新建写入前在事务内判断开放配置、受信账号或有效游客资格。否则返回 `403 ROOM_CREATE_ACCESS_REQUIRED`，无房间或回执写入。普通加入、换房、邀请与重连沿用原权限。 |

口令原文只来自此次成功提交的输入。用与其他用途隔离的 HMAC-SHA256 标签从现有 `SESSION_SECRET` 派生 AES-256-GCM 密钥，随机 96 位 nonce，固定用途及版本作为 AAD，载荷为 UTF-8 口令。密封值放在单独的签名 HttpOnly Cookie（`ravens_room_saved_passcode`，Path `/api/room-create-access/saved`，生产 Secure、SameSite Strict，Max-Age 与现有资格同为 400 天）。验证或成功揭示时续存。解密失败视作缺失，不影响有效开房资格。状态与揭示响应均为 `no-store`。服务器日志、URL、前端持久化、创建意图及错误追踪都不带口令原文。旧资格无需迁移。用户在该浏览器重新验当前口令后才补存。已保存的是换码前的原文时允许查看和复制，显示「旧口令，无法给新浏览器授权」，可输入新码更新保存。清理 Cookie、换浏览器或签名密钥更换后按现行规则重新获取资格。

### 2.2 首页前置弹窗与个人栏

1. 首页点「创建房间」先保留当前页面和焦点，查询授权。入口显示原地忙碌，二次点击复用在途查询。确认账号、开放或已有资格后直接进创建页，默认 7 人。需要口令时打开居中「开房口令」弹窗，固定关闭和「验证并继续」按钮。加载失败原地给「重试」，身份服务失败保留其错误语义，不将已带账号凭据的请求伪判为游客。
2. 输入框 16px、可长按粘贴、关闭自动大小写及拼写、清晰标注开房口令。系统粘贴始终可用，只有存在可用剪贴板接口时展示额外「粘贴」快捷操作，权限拒绝回到手动粘贴。空值聚焦同一输入框，错码在输入旁显示，保留输入可改。等待验码时阻止重复提交。主动关闭或系统返回使旧响应不能再导航，已成功写入同浏览器 Cookie 的资格仍然有效。验码响应成功后续查一次资格及保存状态。资格 Cookie 被拦截时提示允许本站保存浏览器数据，保持在弹窗。仅保存凭据不可用时可继续创建，提示本浏览器未成功保存可复制原文。微信键盘开启时缩减弹层留白，确认始终在可视区域。
3. 创建页移除常驻口令字段。提交时若权限刚被清理或账号退出，暂存昵称、头像及创建草稿，复用同一弹窗。服务器明确拒绝的新建没有回执，可以重新拿创建票据提交。结果不明优先重放原意图，不用验码抢占回执核对。初次进入、加入页、受邀直链始终不弹开房口令。
4. 首页「我的钟楼」及大厅本人资料菜单复用游客口令区块。仅在账号已确认是游客且授权已确认时显示。上版有资格没有原文时显示「已保存开房资格」与「补存口令」。有原文时先显示「查看口令」，显式查看后显示可选中文本框和「复制」。复制在按钮手势中写入，成功短提示，失败选中内容并提示手动复制。关闭弹层、后台、任何账号变化通知或离开房间立即清除内存原文。后台返回先重新确认账号和资格。登录用户无口令区域，即便此浏览器曾为游客验过码。切换身份、响应超时与来回打开弹层用既有账号代数及当前弹层 ID 丢弃晚到结果。微信原生剪贴板权限按真机验收。参见 [W3C Clipboard API](https://www.w3.org/TR/clipboard-apis/)。

口令成功进创建页、从本人菜单打开预览、预览强制退出共用顶层导航交接。现有 `useBackLayer` 会在卸载的微任务中回退历史位置，不能在同一 tick 先卸载旧层再直接 push 新页面。由 App 将来源层标记为「交接中」，先消费其历史条目并等对应 `popstate` 后重核账号代数、房间实例和最新阶段，再打开目标层或创建页。没有来源条目时直接完成，用户已返回或作用域变化时取消待执行的导航。口令补存从账号菜单打开时用同一顶层弹层内的子视图，返回时恢复菜单焦点。

## 3. 人数滚轮和自定义基础构成

### 3.1 手势、画面与反馈

- 以一行机械滚轮替代八颗人数按钮。中间为带纸面质感的数字，两侧露出邻档，边缘有蒸汽机械齿轮。人数 5–12，初值 7，两端停住。手指向左拖露出更大数，向右拖露出更小数。相邻数字、齿轮与拖动位移同一进度渲染。松手约 160–220ms 吸附最近一档，快滑惯性最多额外一档且不过界。直接点击上／下一档同样走吸附。保留两枚 44px 上一档、下一档快捷按钮和键盘箭头能力。
- 横向滚轮用 `touch-action: pan-y`。按下为待定，8 CSS px 且横向位移超过纵向 1.25 倍后锁定，超过 8px 的纵向意图交给页内滚动。只有锁轴前的短点按才触发邻档按钮。拖过一档后的合成点击丢弃。拖动时只跟踪主指针，轴锁后捕获，合并在 `requestAnimationFrame` 内更新 transform。慢拖每跨一整数档响一拍，45ms 内多个过档合并成一拍，吸附同一档不再重响。键盘和按钮用同一提交方向。延迟音频未准备好时只省略该拍，禁止落后补播。音效关闭时持续有视觉反馈。
- 四个数量槽分别显示镇民、外来者、爪牙、恶魔的原创简洁图标与文字，数字上拉增加、下拉减少，合计同步变化。仅数字拖动区使用 `touch-action:none`，从图标、文字和其余区域仍可以滚动表单。每槽 44px 以上，保留点按增减和上下箭头操作。编辑中的可滚数值分别为 0–总人数、0–4、0–2、0–1，允许先改某项再补齐其他项，创建仍按下文校验，最高最低值不循环。人数和四类数字分别提供可访问名称、当前值和上下界。320px 下允许阵容 2×2 排列。系统减弱动态偏好开启时保留直接位移及短吸附，去惯性、蒸汽和装饰转动。
- 正常 `pointerup` 先结束拖动状态、提交吸附目标，再释放捕获。只有拖动尚未结束时收到 `pointercancel`、意外失去捕获、旋转、后台、弹层关闭或第二指加入，才退回本次拖动前的档位与构成并停止排程。非 Pointer Events 环境降级到明确的点击与键盘控件。主页面外壳固定，只有表单内容滚动。合计与错误保留一行位置，按钮固定底部。昵称、头像、输入法适配和原有黑金暗色继续使用。手势与可视区域行为分别参见 [W3C Pointer Events](https://www.w3.org/TR/pointerevents3/) 和 [Chrome 的视口说明](https://developer.chrome.com/blog/viewport-resize-behavior)。

### 3.2 数据和合法性

新增共享 `BaseComposition`，字段 `townsfolk, outsider, minion, demon` 均为整数。首次选某人数使用引擎 `distributionFor(count)`，同一次开房草稿切回该人数保留它的编辑。「恢复默认」只复原当前档位的四数及错误状态。创建完成或明确退出草稿后丢弃临时编辑。已签发并待确认的创建意图冻结人数、模式、构成和资料。

合法基础构成须满足总数等于所选人数、至少 1 镇民、0–4 外来者、1–2 爪牙、恰好 1 恶魔，且存在至少一套能发出的组合。数量不足或超额可暂存和继续调，用「已配 X/Y 人」及差值指出问题，阻止创建。由引擎给出 `COUNT_MISMATCH / COUNT_OUT_OF_RANGE / NO_LEGAL_DEAL`，前后端共用，服务端执行最终判定。效果等同于默认表的配置归一成默认，不作为自定义保存。

对自定义构成，在引擎枚举现有目录中指定数量、互不重复的爪牙集合。每组若含男爵，从镇民转出 2 席给外来者。实际出牌须仍至少 1 镇民，所有类别在角色库存内。无合法组合返回 `NO_LEGAL_DEAL`。部分组合无法抽出时排除该组合，例如基础外来者有 3 位时男爵组合无效，创建页用「当前构成不会抽到男爵」解释。剩余候选以既有种子稳定随机抽取。随后发足镇民、外来者和恶魔，保留酒鬼的虚假镇民身份及镇民足够时的开局信息与主动职责搭配。发生强制选角时只在可包含所选角色的合法组合抽取，最后换到房主席。无解则禁用该角色并显示原因，服务端相同校验，旧选项在依赖改变后不会偷偷变成随机。默认构成的正常随机分配继续使用原算法。

例：8 人 `5/1/1/1` 抽到男爵时实际 `3/3/1/1`。7 人 `4/0/2/1` 可配置，首夜候选依据实际两名爪牙。5、6 人的小局仍按人数规则，只有启用原 6 人协作开关才发同伴和伪装。针对自定义局的首夜恢复验证，从冻结的基础构成读取爪牙数量，老快照继续按原人数表验证。首夜初始同伴席以原 `startInfo.initial` 为准，之后真实恶魔传位不重写初始数据。玩家视图只显示「基础构成」，抽到男爵、实际阵容和调试自选角色不会提前成为普通公开信息。

## 4. 单人调试房和指定身份

### 4.1 开关、房间和入口

- 首页复用标题三击识别，同一标题三次点击、相邻间隔不超过 450ms。先确认当前没有已进入教学或进行中的本人对局、没有未决创建或关键房间写入，再切换设备偏好 `ravens.debugMode.v1`。中央文字约 1.4 秒淡入淡出，无确认按钮、不截触摸，同一时刻只出现一条。存储失败本次页面继续可用，提示刷新后可能恢复默认。首页显示轻量「调试模式」和创建入口状态。
- 调试开房沿普通授权、资料和人数流程，提交时固化房型。创建后的大厅标「单人调试」，有一个真人及人数减一名人机。人机头像按现有随机种子策略选择，维持唯一性，身份在开局发牌。所有人机入座即准备完成，房主自己按「准备并开始」。房间没有邀请入口、分享码操作、公共大屏、账号认领的跨身份入口。普通玩家既不能作为真人占调试席，也不能从其他房换入。调试模式开启时从首页主动去加入普通房，先提供退出调试再加入。邀请参数保留到确认退出，操作失败不修改来源房间。
- 大厅点自己的头像，资料菜单保留昵称头像编辑，增加「选择测试角色」「动画演示」和「退出调试模式」。选角在同一资料弹层内显示二级视图，返回时恢复菜单位置。普通大厅照常可修改昵称头像、手动补人机，界面不渲染调试专属按钮。点击退出时关闭该调试大厅并回首页，先确认「关闭当前单人调试房并退出」，仅服务端确认关闭后更新偏好。失败保留原大厅和偏好。首页再次三击若仍保留调试大厅，走同一确认路径。教学与游戏进行中不显示退出，从房间菜单返回首页保留席位，原中止本局仍是独立动作。调试房隐藏通用离开入口，防止借它跳过退出阶段。回首页仍保留席位、未同步完或离线时先核对原房间阶段。
- 当前确认显示「随机」或所选角色。按镇民、外来者、爪牙、恶魔展开，选择时显示公开说明和是否适配配置。只允许房主指定自己；按酒鬼能力发真实酒鬼及可感知镇民。开局按真实发牌和可见范围运作。下一把保留调试房型、基础构成与仍合法的自选角色。新房的选角仅调试房提供；既有房间的合法旧选择继续在原对局或重启原房间时生效。普通房不新增保留中的选择。创建、重置、选角色、调整六人邪恶协作及换座等所有修改 setup 的路径均在同一事务内恢复调试人机已准备，房主准备清零。暂停、人工计时或调度器未启动时也成立。

### 4.2 创建、恢复及防重

- 数据仍写已有房间快照和创建回执表。默认房继续快照 5。使用单人调试、或使用非默认基础构成的房间写快照 6，持久化 `setupOptions:{version:1,kind:"STANDARD"|"DEBUG_SOLO",baseComposition?}`，房型和基础构成自创建起不改。快照 6 仅被能识别此选项的后端读写。普通房默认及快照 1–5 沿现有迁移。修正 `LiveRoomRuntime.initialize` 的「非 5 都是旧快照」判定，只迁移本次确实从可识别旧格式转换的值。6 版 restore 验证范围、房型、座位及基础构成。单人房任何存续快照只有一个人类且为房主，不允许展示席；不存在不满的单人房持久快照。快照 6 进入老服务前须判为不兼容。扩展 `RoomView` / `RoomSummary` 的可选 `roomKind` 和 `baseComposition`，缺省为普通房及引擎默认构成。具有房主席位时调试摘要返回 `canJoin:false,willReplaceBot:false`，首页与 URL 恢复先匹配现有席位。调试局记录始终带既有 `rehearsalUsed:true`。
- `POST /api/rooms` 新增 `creationVersion:3`。已有 `playerCount, organizerName, createTicket, sixPlayerEvilCooperation?` 继续，新增 `roomKind:"STANDARD"|"DEBUG_SOLO"`、`baseComposition?:BaseComposition`，单人模式另带 `hostAvatar:string|null, expectedProfileRevision?:number`。普通默认创建可继续用原 v2。v3 普通房返回原凭据与可识别的房型，沿原创建后自动入座。v3 单人调试返回 `{code, roomInstanceId, creationId, roomKind:"DEBUG_SOLO", participantId}` 并设置该席位的签名 `ravens_player` Cookie，客户端直接进入已入座恢复段，不追加普通 join。
- 服务端单个 `LiveRoomRuntime.execute` 先校验创建身份、命令编号、票据、权限和参数。用固定字段顺序算 v3 指纹，包含房型、归一化构成和用于创建的资料（含头像和资料修订号）。旧 v1/v2 指纹算法逐字保持。单人调试在同一操作内创建房间、生成原房主席位并绑定账号或原游客身份、完成头像选择、占用人机额度、补齐并准备、人机资料与创建回执一并提交。超过现有人机额度返回 `429 BOT_LIMIT_REACHED`，写入全部撤销。资料冲突遵循既有权威资料版本反馈。保存失败返回既有 503，任何读取和 WebSocket 都看不到半房。
- 每次创建沿现行票据、`x-command-id` 和持久回执模式。v3 的根路径 `POST /api/rooms` 重放须仍为票据绑定的账号 subject，或无账号且持有匹配的原游客创建上下文。现有房主席 Cookie 只发送至其房间级路径，持该 Cookie 时通过房间级 `/me` 恢复，不扩大 Cookie 路径。v3 创建回执 payload 增加 `creationVersion:3, roomKind, hostParticipantId?`，调试房必含 hostParticipantId。恢复时校验实例仍一致且人物仍为原房主。游客首建和重放以创建键、实例派生同一房主席凭据。账号首建和重放复用既有账号席位派生凭据，与同账号恢复后的凭据一致。回执不能覆盖已失效或转移的席位。过期或失效时返回可区分错误，前端不自动新建。
- 同 ID 改房型、构成或资料返回 409，已关闭房间回执返回 410。回执仍在保留期而票据时限已过时走回执恢复。客户端保存带账号作用域且冻结的待确认意图，不含口令和席位凭据。普通房继续使用原 `sessionStorage` 待确认槽，老 v1/v2 意图按原语义恢复。调试 v3 意图在发 POST 前复制到 `localStorage` 的 `ravens:debug-create:v1:<账号作用域>:<创建ID>`，含原请求和首次发送时间，最长 24 小时。不同创建 ID 的记录不互相覆盖。切账号隐藏其他账号的记录。恢复时先同步现有已知席位；没有可恢复的席位时，对单条未决意图走原请求，对多条显示「继续核对开房」列表，用户按人数和发起时间选择其中一条。服务器校验原创建身份，失败不自动发新建。收到成功答复后，须确认 `saveSession` 已写入可跨关闭恢复的存储，并按同一账号作用域读回房间实例和席位，才移除对应 ID 的意图。只保存到内存不算成功。明确终态也可以清理对应 ID。禁用持久化存储时提示该页仍可重试，完全关闭后未收到房号的结果可能无法自动找回。单页连点合并为同一动作，多标签恢复同一 ID 不重复创建。不同标签独立确认开的不同 ID 是独立操作，仍受现有房间人机额度，验收与重放分开。
- 保留普通 `/api/rooms/:code/rehearsal/role` 命令编号和 version/context 校验链，写入为调试大厅房主专用，允许 roleId 或 null。校验可包含该角色的阵容，用命令回执避免重复选择，迟到指令不能跨过开局或下一把。失败保持原选择，房间变化先同步。单人房前端隐藏移除和清空人机，服务端同时拒绝修改人数的 bot 命令及通用 `removeParticipant`，包括带取消教学参数的请求。暂停、继续、单步仍使用调试工具。正式房现有合法手动机器人功能保留。

### 4.3 普通入口与调试隔离

创建房主通过已提交创建回执、新席 Cookie 或同一账号已有席位恢复。调试房禁用通用恢复码和游客座位认领，避免通过其他身份转移房主席。账号同一 subject 从已有记录恢复仍是同一个席位。退出复用 `DELETE /api/rooms/:code/leave`，为命令体增加 `intent:"EXIT_DEBUG"` 可选字段。服务器在同一执行事务中按顺序校验参与者身份与原房间实例及房主所有权，核对房型与 LOBBY 阶段，再校验 setup、命令版本并删除。这个分支在通用命令版本预校验之前检查阶段，权限检查始终先于阶段判断。调试房的无 intent 通用退房拒绝，普通房保持原处理。开局先成功时退出请求返回 `409 GAME_IN_PROGRESS`，保留偏好及原席。仍在大厅但命令版本过期时先同步，并由房主重新确认。退出先成功时后续开局找不到原实例。删房后原房内回执也消失。等待响应超时后重试同一命令，只有已收到成功或查询确认该房号不存在／已换成其他实例，并且本地没有更新的调试上下文时才结束退出。泛 403 或网络错误保留待确认。该流程无房主移交，不操作普通房。

在调试房早于公开投影 fallback 检验成员权限。有效游客房主席 Cookie 与有效账号房主席均可查自己的 summary、房间视图、`/me`、`/result` 和玩家 WebSocket。无有效房主席或请求 DISPLAY 时返回 `403 DEBUG_ROOM_PRIVATE`，WebSocket 握手按现有权限错误关闭。拒绝公开 join-ticket 及加入。通用换房的签发和消费均检查来源及目标，任一为调试房即拒绝。不带人机和席位信息，不写来源房间。调试大厅去普通房先以专用命令关闭原调试大厅，再按原邀请加入。账号同一 subject 的房间列表及账号恢复使用原有本人路径。邀请路由识别 `DEBUG_ROOM_PRIVATE` 为终态，清掉该目标邀请并留在原房间或首页，给「这是单人调试房，无法加入」，不显示重试加入。底层新玩家加入函数同样禁止调试房增添第二真人或展示席，创建事务通过专用首席初始化路径。调试偏好不是免码资格，也不打开普通私密信息。

## 5. 调试大厅预览

预览挂在已完成同步的 `RoomApp` 下，入口判定为本机调试开关打开、当前服务器投影为 `DEBUG_SOLO` 的 LOBBY、当前玩家为房主。正常大厅、教学或对局不挂载预览。旧 `?preview=effects`、候选试听目录式 URL 和它的 `index.html` 入口统一进入同一受守卫的路径，旧 HTML 不保留独立播放器，参数不能自行打开调试。缺少权限时清掉预览参数，按原流程回当前对局或首页，不渲染目录。游戏原本需要的媒体仍由静态路径分发，此处限制的是预览功能入口。

- 固定页头左侧「返回游戏」，右侧「动画｜音频」和音符。无论是否在演出播放中都保留页头。预览使用独立层级，声音弹窗及遮罩高于演出、播放控制和固定页头，打开即让底层控制 `inert`。正式局关键演出关闭音符层的规则只作用于真实对局，预览演出中仍能调音。保留底层大厅和 room feed，退出回同一实例和大厅。系统返回先退出声音或当前详情，再退出预览。跨页、切房或其他标签页开局，停止演出并按第 2.2 节交接历史层，再显示当前合法阶段。后台、bfcache 恢复和暂时断线暂停播放权限，先取得同实例最新 LOBBY 和房主快照才可继续试听。页面自身不纵向滚动，目录使用一个内滚动区。
- 动画按「角色专属／通用」分区。角色专属用四类角色筛选，子类可按「信息获取、行动、首夜」切换，场景可有多标签。通用含入夜、天亮、有／无人处决、提名／投票、枪击的公开演出及善恶胜利等既有场景。保留真实游戏组件、播放、暂停、重播、进度和调试单步。目录用公开脚本和固定虚拟头像，不读房间私密数据，不提交游戏写操作。列表清单枚举现有正式演出和公开调试夹具，缺项用覆盖检查报出。
- 音频页分「背景音乐、音效与环境声、候选素材」，音效可按动作、按钮／翻页、提示、角色与版本查找。以现有 `apps/web/public/audio` 和 `public/audio-candidates` 音轨生成可验证清单。当前目录有 132 个正式目录及历史版本 MP3、55 个候选 MP3，合计 187 个文件应均能通过一个可找到的条目试听。按路径给 ID，打上已用、历史、候选标签并保留原名称、来源和许可跳转；压缩内容相同的条目可合并展示，但版本需可选。源目录有增删时同步生成清单，新增文件无映射、清单指向缺文件作为构建验证失败。所有文件可单独播放、暂停和拖进度，失败显示该条重试，列表本身不下载音频。长音轨流式加载。切新条目、切页、后台和退出时停止旧播放，晚到的解码和媒体完成回调不能复活旧声音。

## 6. 统一音符控件与声音

现有音符都变为打开同一个 `AudioSettings` 层。主页、创建／加入、大厅、手册、城镇、公共大屏和调试预览有各自局部的合适位置。城镇保持在角色名左侧，身份确认和遮住私密的全屏阶段沿用现有限制。底栏、叠在其他关闭按钮上以及重复「声音设置」按钮不新增。删除房间菜单中的音频设置条目及重复入口，局内「私密操作音效」切换迁入音符层，创建／加入原有线上线下选择保持。

同一面板通过正式及预览两个设置适配器展示「音乐」和「音效」各自的开关、音量，替换现有预览态无法在面板调节的只读分支。总静音沿已有总开关偏好保留，可从同层恢复原通道设置。音量滑块立即作用于对应 Gain，播放进度不重置。正式和大屏继续以各浏览器现有设备偏好为准。演示使用独立预览会话，默认音乐和音效均开启、初始音量沿正式默认值（音乐 .8，音效 .72），本次更改不覆盖正式设置，切两个预览页保留当前会话偏好。正式私密音效仍服从参与方式的静音限制，纯虚拟预览可试听。面板通过单个可控 portal 挂载，使用同一个返回层与焦点归还规则。遇到角色确认、必须全屏的公开演出、私密遮盖或预览失去资格，关闭面板并让位。手册启用音效时在同一点击手势尝试解锁，成功后预热纸声；首次读页和重开手册共用此路径。

第一次点击「动画演示」或「播放」时同步尝试音频上下文恢复及媒体播放，先做解锁再等待资源。若宿主拒绝，保留播放控制和轻量「点一下开启声音」提示，用户再点可重试。演出可静音继续，名单加载不依赖音频解锁。不要求网页自己绕过微信限制，真机测试 iOS 及 Android。正式配乐、演示配乐、点播音轨和当前演出声音的启停有清楚负责人，试听进入或离开时不会双播。参见 [WebKit 媒体播放说明](https://webkit.org/blog/6784/new-video-policies-for-ios/) 与 [Chrome 自动播放政策](https://developer.chrome.com/blog/autoplay/)。

## 7. 实施顺序、兼容与发布

1. 先落共享阵容规则、房型和快照，再完成口令服务端、幂等开房和调试入座权限。先独立审查入座路径及快照恢复，再开放前端新房型入口。
2. 接首页授权、个人栏、滚轮和阵容，再接大厅选角、退出和已有房间恢复。录制 320/375/390px 及横屏短高设备交互，至少验证一次输入法弹出时的位置保持。
3. 最后接预览双页签、清单与音符统一。用同一设备分别验正式音量、纯调试预览、手册翻页和私密静音。先运行定向核验并复用未变的规则和生产构建证据，再安排微信真机。
4. HTTP/WS 协议保持 7，v3 创建为新增能力。旧客户端可继续普通开房、加入及恢复。新版服务器在 `GET /api/room-create-access` 所有正常状态上附加 `creationV3:true`，作为本批口令和创建能力的声明。新版页面遇到旧服务，冻结调试、阵容编辑和可复制口令操作并显示刷新提示。老服务明确允许开房时仍可普通默认 v2。已登录用户遇到旧服务要求口令时提示「服务更新中，请稍后刷新」，不弹游客验证。已提交的 v3 意图核对原版本能力，保留原意图并等待服务恢复，禁止降级成 v2 重发。
5. 现有口令配置、登录底座、公开邀请码、头像资料和业务数据库结构保持。上线前重核共享规范，使用全局锁、固定提交和本项目部署流程。没有 6 版快照且无待恢复 v3 回执时可以恢复旧服务；存在新标记时优先前向修复，禁止直接用旧版加载新快照、清房或回档。备份和回退条件写进发布证据，私密密钥和配置值不进记录。README、房间规则、阶段和部署记录随实现核对；不在这批改动投票流程。
