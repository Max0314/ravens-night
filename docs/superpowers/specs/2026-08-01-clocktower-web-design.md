# 全自动说书人 Web 游戏设计规格

日期：2026-08-01  
状态：待用户书面确认  
部署形态：Docker Compose，自有服务器与域名

## 1. 产品目标

构建一套适合全新手面对面聚会的多端 Web 阵营推理游戏。所有真人都是玩家，不设置真人 DM。服务端承担身份分配、夜序、信息生成、提名、投票、死亡、特殊能力和胜负裁决。

现场只有一台公共电脑。公共电脑显示所有人均可知道的城镇广场；每位玩家使用手机查看私密身份、接收信息并完成夜间操作。所有设备通过相同的六位邀请码加入同一房间。

成功标准：

- 5–12 名第一次接触游戏的玩家能够在不阅读长规则书的情况下完成一局。
- 无真人拥有秘密后台、裁决权或超出其角色的游戏信息。
- 玩家刷新、手机短暂断线或服务容器重启后能够恢复同一局游戏。
- 公共端不会收到隐藏角色、夜间目标、醉酒、中毒或阵营数据。
- Docker Compose 在配置域名与环境变量后能够完成 HTTPS 部署。
- 视觉达到可正式使用的游戏产品质量，不呈现后台管理工具观感。

## 2. 首版范围

### 2.1 包含

- 组织者账户注册、登录和房间管理。
- 玩家以昵称和邀请码访客加入。
- 公共大屏以邀请码加入，经大厅玩家确认后绑定。
- 5–12 人固定新手角色包。
- 全自动身份配置、首夜、后续夜晚、白天讨论、提名、投票、处决和胜负结算。
- 互动式全新手教学与按需规则帮助。
- 私密玩家端、16:9 公共端、组织者房间列表。
- 实时在线状态、断线暂停、自动重连、事件重放。
- 中文界面；代码和数据结构保留本地化扩展点。
- 原创“午夜钟楼”UI、角色立绘和场景资产。
- 对局结算后的身份揭晓和事件时间线。

### 2.2 首版不包含

- 真人说书人模式或后台人工干预。
- 自定义角色、自定义剧本、旅行者和复杂扩展角色。
- 语音或视频通话；面对面讨论直接进行。
- 玩家间站内私聊；私下交流在线下进行。
- 匹配大厅、公开房间列表、排行榜、付费、商城或社交关系。
- 多实例水平扩展。首版单 App 实例，避免引入 Redis 和分布式房间锁。
- 原生 iOS/Android 应用；Web 以可安装 PWA 形式提供。

## 3. 权限与身份模型

### 3.1 组织者

组织者使用用户名或邮箱与密码登录，可以创建、查看和关闭房间。组织者进入房间后也是普通玩家。

游戏开始前，组织者可以：

- 创建房间并选择 5–12 人规模。
- 显示或重新生成邀请码。
- 移除尚未绑定座位的异常访客。
- 发起“全员准备”和“开始教学”。

游戏开始后，组织者不再拥有影响游戏的特殊能力，不能查看角色、改变状态、跳过角色行动或指定裁决结果。系统只允许全体玩家一致同意的暂停或终止操作。

### 3.2 玩家访客

玩家无需账户，以昵称和邀请码加入。服务端签发随机、不可预测的玩家会话和重连令牌；令牌只保存在该设备的 HttpOnly Cookie 中。

大厅阶段可以更改昵称和座位。游戏开始后，玩家会话与座位永久绑定，直到本局结束。玩家 API 只返回自己的秘密信息与所有人都能看到的公开信息。

### 3.3 公共大屏

公共大屏输入相同邀请码并选择“大屏模式”。大厅中的玩家必须确认新出现的大屏请求，防止远程旁观者仅凭邀请码观看。

服务端为大屏签发单独的只读 display session。大屏只能订阅 PublicGameView，不存在任何可获取私密状态的接口。

### 3.4 管理员

部署管理员只负责账号封禁、资源限制与服务运维。管理 API 不提供进行中对局的明文身份或夜间秘密。需要故障排查时使用事件编号、错误类型和脱敏日志。

## 4. 用户流程

### 4.1 创建和加入

1. 组织者登录并创建房间。
2. 系统生成六位易读邀请码，排除 `0/O`、`1/I/L` 等混淆字符，并显示二维码。
3. 玩家打开域名，输入邀请码或扫码，在手机上输入昵称。
4. 大屏打开同一地址，输入邀请码并选择“公共大屏”。
5. 玩家在大厅确认大屏请求。
6. 玩家依次选择座位；系统显示在线状态和设备是否完成音效/震动测试。
7. 达到配置人数并全员准备后进入教学。

### 4.2 新手教学

教学总时长目标为 3–5 分钟，采用渐进披露：

1. 30 秒：善良与邪恶阵营目标。
2. 45 秒：夜晚、白天及手机操作。
3. 45 秒：死亡后仍可讨论，但仅剩一张幽灵票。
4. 60 秒：不影响正式对局的模拟提名与投票。
5. 私密阶段：每位玩家查看自己的身份教学卡。

每个公共教学步骤要求所有手机点击“我明白了”。身份教学卡包含：阵营、能力白话解释、一个具体例子、三条新手建议，以及“不要向别人展示屏幕”的提醒。

正式游戏第一次出现以下行为时，展示一次性情境提示：夜间选择、获得信息、提名、被提名、投票、死亡、使用幽灵票。玩家随时可以打开“现在该做什么？”和规则词典。

### 4.3 正式游戏

1. 服务端生成一次性随机种子、角色配置和座位身份。
2. 玩家分别确认私密身份。所有人确认后进入首夜。
3. 夜间所有手机统一进入“村庄沉睡”遮罩。当前行动者收到震动和私密操作界面；其他人看到相同的无信息等待动画。
4. 服务端按夜序处理动作与信息，将结果仅发送给对应玩家。
5. 黎明时公共屏公布夜间死亡名单和公开事件。
6. 白天进入可配置倒计时的面对面讨论。
7. 存活玩家在手机上发起提名。被提名者获得辩护倒计时。
8. 系统按座位顺序运行投票，手机显示举手/不举手；公共屏实时显示公开票数。
9. 服务端维护当前处决席，白天结束时执行处决并判断胜负。
10. 未结束则进入下一夜；结束则公布胜方、全部身份与可公开事件时间线。

## 5. 游戏状态机

房间必须处于下列单一状态之一：

`LOBBY → TUTORIAL → ROLE_REVEAL → FIRST_NIGHT → DAWN → DAY_DISCUSSION → NOMINATION → VOTING → EXECUTION → OTHER_NIGHT → … → GAME_OVER`

辅助状态为 `PAUSED_FOR_RECONNECT` 和 `ABORTED`。暂停保留原阶段与剩余计时，恢复后返回原状态。

每次状态转换由命令触发，规则引擎验证后产生不可变事件。客户端不能直接修改状态，只能提交命令。例如 `SubmitNightTarget` 产生 `NightTargetLocked`，`CastVote` 产生 `VoteRecorded`。

同一房间的命令由内存串行队列逐个执行。事件在数据库事务中写入后才广播。每隔固定事件数量和每次阶段转换保存状态快照。服务重启时读取最新快照并重放其后的事件。

## 6. 角色与人数配置

首版支持 5–12 人，基础数量如下：

| 玩家数 | 镇民 | 外来者 | 爪牙 | 恶魔 |
|---:|---:|---:|---:|---:|
| 5 | 3 | 0 | 1 | 1 |
| 6 | 3 | 1 | 1 | 1 |
| 7 | 5 | 0 | 1 | 1 |
| 8 | 5 | 1 | 1 | 1 |
| 9 | 5 | 2 | 1 | 1 |
| 10 | 7 | 0 | 2 | 1 |
| 11 | 7 | 1 | 2 | 1 |
| 12 | 7 | 2 | 2 | 1 |

角色包采用数据驱动清单，但角色能力由有类型的规则模块实现，不能用任意脚本执行。可改变外来者数量的角色在角色抽取前运行 setup modifier。

角色能力模块至少实现：

- 首夜信息：二选一身份线索、外来者线索、爪牙线索、邪恶相邻对数量等。
- 每夜信息：邻座邪恶数量、二人侦测及红鲱鱼、处决身份回看。
- 主动能力：公开一次性点杀、夜间选择与保护。
- 被动能力：免疫恶魔击杀、首次被镇民提名触发、投票受主人限制。
- 死亡触发：夜间死亡后选择玩家并查验。
- 邪恶干扰：持续到次日黄昏的中毒、额外外来者、恶魔死亡接替、间谍式错误登记。
- 特殊胜负：关键善良角色被处决、三人存活时无处决获胜等。
- 恶魔能力：夜间击杀、自杀传位、恶魔伪装信息。

## 7. 全自动说书策略

传统真人说书人可决定错误信息、登记结果和部分重定向。全自动版本把这些裁量实现为可测试的受约束策略。

### 7.1 原则

- 合法：结果必须是角色规则允许的结果。
- 不泄密：错误信息不能通过格式、延迟或文案暴露醉酒、中毒等隐藏状态。
- 可推理：避免持续制造逻辑上完全无解的世界。
- 不偏袒：策略不能读取玩家聊天或现实表现，也不能针对某一真人。
- 可重放：所有随机选择来自对局种子与事件序号。
- 有变化：同样配置的不同对局不能总产生相同误导模式。

### 7.2 错误信息生成

每个信息角色定义合法结果集合。正常状态返回真实结果；醉酒或中毒时，策略从合法集合选择结果，优先级为：

1. 与真实结果不同，但仍存在至少一个可解释世界。
2. 避免连续多夜固定给同一方向的明显模式。
3. 避免直接、无反制地锁定恶魔或直接证明某玩家中毒。
4. 若没有合适假结果，允许返回真实结果。

信息选择过程记录为私密审计事件，游戏结束后可在完整回放中解释。

### 7.3 错误登记与重定向

可被登记为其他阵营或类型的角色，在每次查验时独立调用 registration policy。策略结合查验类型、存活人数和当前公开信息，选择规则允许的登记值。

保护、免疫和击杀重定向严格按优先级表解析。若存在多个合法重定向目标，使用种子化随机并排除会导致非法循环的选择。

### 7.4 超时策略

- 普通私密行动默认 60 秒，可由房间设置在 45–120 秒调整。
- 30 秒时震动提醒；超时后再给予 30 秒宽限。
- 当前行动者离线时不倒计时，进入断线暂停。
- 在线但主动超时：信息角色自动确认；选择角色从合法目标中种子化选择。首次超时教学会明确警告。

## 8. 提名、投票与胜负

- 每名存活玩家每天最多提名一次、被提名一次。
- 死亡玩家不能提名。
- 投票门槛为当前存活人数的一半向上取整。
- 最高有效票数进入处决席；后续必须严格超过才替换。
- 并列最高票数时无人处决。
- 存活玩家可以参与每次投票。
- 死亡玩家整局只保留一张幽灵票，使用前二次确认。
- 受主人投票约束的角色只能在主人当次举手时计票。
- 每天最多执行一次处决。

规则引擎在每个死亡、身份接替、处决和阶段结束事件后运行胜负判定。角色特殊胜负优先于通用阵营胜负；冲突顺序由显式优先级测试固定。

## 9. 前端信息边界

服务端提供三个互不继承的视图模型：

- `PublicGameView`：阶段、公开座位、存活状态、公开事件、倒计时、提名和票数。
- `PlayerGameView`：PublicGameView 加本人的角色卡、本人可用动作、本人收到的信息和本人幽灵票状态。
- `OrganizerView`：只在大厅增加创建、移除未入座访客和开始教学能力；正式开始后降级为 PlayerGameView。

公共页面的 JavaScript 包中可以包含通用角色词典，但进行中房间的 API 和 WebSocket 消息不得包含任何隐藏实例数据。前端不以“收到后隐藏”的方式保护秘密。

## 10. UI 与角色美术

### 10.1 风格

采用已确认的原创“午夜钟楼”方向：哥特建筑秩序、木刻版画线条、克制手绘上色。气氛神秘、庄重、精致，但不血腥，不使用廉价恐怖效果。

核心色板：

- 夜幕黑 `#080B12`
- 深海蓝 `#121A28`
- 古金 `#B58B43`
- 羊皮纸 `#EEE4CD`
- 暗红 `#8F303B`

标题使用具有仪式感的中文衬线字体；正文使用高可读中文无衬线字体。手机正文不小于 16px，关键按钮触控区域不小于 44×44 CSS 像素。

### 10.2 角色立绘

首版制作 22 张统一规格原创半身立绘。所有角色采用一致的光照、构图和精细度，不以面相、明暗或颜色暗示善恶阵营。角色通过轮廓、职业道具和有限的个人点缀色区分。

每张立绘输出：

- 角色卡用 4:3 或 3:4 主裁切。
- 64–128px 圆形头像裁切。
- 24–32px 极小徽记或轮廓替代图。
- AVIF 与 WebP 多尺寸版本。

角色图需通过 64px 缩略图辨识测试、色盲模拟和阵营暗示评审。不能直接复刻任何现有桌游官方素材。

### 10.3 场景与动效

提供首页夜村、夜间钟楼、黎明广场和结算长桌四类响应式背景。烛光、薄雾、钟摆和纸张纹理为低频氛围动效，不阻塞操作。

尊重 `prefers-reduced-motion`。低性能模式关闭粒子、视差和模糊滤镜。首屏只预加载关键背景与本人角色资源，其余按阶段懒加载。

### 10.4 大屏与手机

公共屏优先支持 1920×1080 和 3840×2160，座位、昵称、倒计时与票数必须在三米外可读。不得依赖 hover。

玩家端优先支持 360×640 至 430×932 竖屏，也需在横屏和桌面浏览器可用。私密信息页面具有防旁观提示，可点击快速遮罩，但不宣称阻止截图。

## 11. 技术架构

采用 pnpm TypeScript monorepo：

```text
apps/
  web/          React + Vite PWA
  server/       Fastify HTTP/WebSocket 服务
packages/
  contracts/    命令、事件和视图模型 schema
  game-engine/  纯 TypeScript 规则引擎
  content/      可替换角色元数据和本地化内容包
  ui/           设计 token 与共享组件
tests/
  e2e/          Playwright 多设备场景
deploy/
  Caddyfile
```

服务端采用 Fastify、WebSocket、PostgreSQL。输入输出使用 JSON Schema/TypeBox 或等价方案运行时校验。数据库访问使用支持类型安全迁移的轻量方案。

不引入 Redis、消息队列、微服务或 Kubernetes。单 App 实例足以满足私人和小规模公开访问。若未来水平扩展，再将房间协调器迁移到分布式锁与发布订阅层。

## 12. 数据模型

核心表：

- `users`：组织者账号、密码哈希、状态与时间戳。
- `sessions`：组织者会话哈希、过期时间和最后活动时间。
- `rooms`：邀请码哈希、组织者、配置、当前状态和过期时间。
- `room_participants`：昵称、座位、会话哈希、在线状态、玩家/大屏类型。
- `games`：角色包版本、随机种子密文、事件版本和状态。
- `game_events`：游戏、递增序号、事件类型、公开载荷、私密加密载荷、时间戳。
- `game_snapshots`：事件序号、完整状态密文和校验和。

邀请码只存哈希。玩家令牌、会话令牌只存哈希。快照与私密事件使用服务端密钥进行应用层加密。日志不记录邀请码、Cookie、身份载荷或夜间目标。

## 13. 实时协议

HTTP 用于登录、建房、加入、恢复和提交具有幂等键的命令；WebSocket 用于状态推送、倒计时同步和在线状态。

每个客户端维护：

- `connectionId`
- `roomId`
- `lastEventSeq`
- `viewRevision`

重连时客户端提交最后事件序号。服务端发送增量公共/私密视图，差距过大时发送完整授权视图。所有写命令携带 `commandId`；服务端对同一玩家的重复 commandId 返回原结果，避免双击和重试重复执行。

## 14. 异常处理与恢复

- 非当前行动者断线：显示离线状态，保留座位十分钟，游戏可以继续讨论。
- 当前夜间行动者断线：立即暂停秘密阶段；公共屏只显示“等待玩家重连”，不暴露行动角色。
- 玩家刷新：Cookie 自动恢复；若 Cookie 丢失，只能在大厅用一次性恢复码迁移。正式游戏中不允许管理员读取并转移秘密。
- 大屏断线：游戏继续，重新输入邀请码并由玩家确认可恢复公共屏。
- App 容器重启：从快照和事件日志恢复相同随机状态；所有客户端重连。
- PostgreSQL 不可用：停止接受命令，不进行仅内存结算；恢复数据库后继续。
- 版本升级：进行中的游戏固定使用创建时的角色包和引擎规则版本。

## 15. Docker Compose 部署

Compose 服务：

- `caddy`：80/443，自动 TLS，反向代理 WebSocket，持久化证书。
- `app`：构建 React 静态资源并运行 Fastify 服务，非 root 用户，健康检查。
- `postgres`：固定主版本，持久卷、健康检查、仅内部网络开放。

环境变量至少包括：

- `APP_DOMAIN`
- `DATABASE_URL`
- `POSTGRES_PASSWORD`
- `SESSION_SECRET`
- `DATA_ENCRYPTION_KEY`
- `ADMIN_BOOTSTRAP_EMAIL`
- `ADMIN_BOOTSTRAP_PASSWORD`

交付 `.env.example`、备份/恢复说明、数据库迁移命令和升级回滚说明。生产 Compose 不暴露数据库端口。启动顺序依赖健康检查而非固定 sleep。

## 16. 安全与滥用防护

- Argon2id 密码哈希；HttpOnly、Secure、SameSite Cookie。
- 登录、建房、加入和邀请码尝试分级限流。
- 严格 CSP、CSRF 防护、输入长度限制和昵称规范化。
- WebSocket 建连及每条命令重新授权，不能信任客户端声明的座位。
- 公共与私密 schema 分离，并用自动测试扫描隐藏字段。
- 房间默认 24 小时后过期；已结束对局按配置保留或删除。
- 不采集语音、视频、通讯录或精确位置。
- 所有随机安全令牌使用密码学安全随机源；游戏随机另使用记录种子的确定性 PRNG。

## 17. 测试策略

### 17.1 规则引擎

- 每个角色能力的正常、死亡、醉酒、中毒和交互顺序单元测试。
- 5–12 人角色数量与 setup modifier 属性测试。
- 任意合法命令序列不能出现双座位、负幽灵票、重复处决或非法胜负。
- 相同种子与事件序列必须产生字节级等价状态。
- 快照前后重放结果一致。
- 自动说书策略只生成合法结果，且不以格式差异泄露干扰状态。

### 17.2 API 与权限

- PublicGameView 序列化不包含禁止字段。
- 玩家 A 无法获取玩家 B 的角色、信息和目标。
- 组织者在开局后无法调用大厅特权命令。
- 重复 commandId 不产生重复事件。
- 伪造座位、修改邀请码、过期会话和跨房间 WebSocket 被拒绝。

### 17.3 多端 E2E

Playwright 同时启动 5、8、12 个手机浏览器上下文和一个 1080p 大屏：

- 完成加入、选座、教学、身份确认和至少两个昼夜循环。
- 覆盖正常处决、并列无人处决、幽灵票和至少一个特殊胜负。
- 在夜间目标选择、投票和黎明三个节点模拟刷新与断网。
- 在事件写入后重启 App 容器并验证恢复。
- 检查 360×640、390×844、430×932、1920×1080 和 3840×2160 截图。
- 检查横屏、虚拟键盘、触控目标、文本溢出和 Reduced Motion。

### 17.4 部署与性能

- 全新数据卷执行 `docker compose up -d --build` 冒烟测试。
- 健康检查、迁移、TLS/反代配置和 WebSocket 升级测试。
- 目标负载：20 个并发房间、每房间 13 个连接，状态广播 P95 小于 300ms。
- 断电式 PostgreSQL 重启不产生已确认事件丢失。
